## なぜWindowsが重くなるのか

パソコンが重い原因と対策
![パソコンが重い原因と対策](images/IG-PRO-01.jpg)

Windowsパソコンは一般的に年数が経つにつれて動作が遅くなる傾向があります。アップデートのたびにOS（オペレーティングシステム、パソコンやスマホを動かすための土台となる基本ソフト）が徐々に肥大化し、古いハードウェアで処理が追いつかなくなるからです。

たとえばRAM（Random Access Memory、ランダムアクセスメモリの略でパソコンが使っているデータを一時的に置いておく作業机）が4GBしかないパソコンでは、Windowsの起動だけでメモリの大半を消費してしまい、ブラウザを開くのも一苦労になります。

古いPCのHDD問題：Windows対Linux
![古いPCのHDD問題：Windows対Linux](images/IG-PRO-02.jpg)

パソコン買い替えの前に、もうひとつの選択肢があります。OSそのものを軽量なLinuxに変えることです。HDD（ハードディスクドライブ、データを長期保存しておく本棚のようなもの）などのハードウェアはそのままでも、OSを入れ替えるだけでもパソコンは生まれ変わります。

![古いパソコンをLinuxで高速化](images/IG-PRO-03.jpg)

## Linuxとは何か

Linux（リナックス）はWindowsやmacOSと同じような働きをするソフトウェア（OS）です。実は、世界中のサーバーの95%以上、スマートフォン（Android）、テレビ（スマートTV）など、あらゆる場所で使われています。

### なぜXfceエディションなのか

Linux MintにはCinnamon（シナモン）、MATE（マテ）、Xfce（エックスエフシーイー）の3つのエディションがあります。代表的で最も人気があるのはCinnamonエディションです。

Xfceは3つのエディションの中で最も軽量で、古いパソコンや4GBメモリの端末でも軽快に動作します。ペンギンコンピュータは「動作が重くなったパソコンを再生する」ことを事業目的としているので最軽量デスクトップ環境であるXfceエディションを推奨しています。

本書のすべてのスクリーンショットと手順はXfceエディションの画面で解説しています。CinnamonやMATEをお使いの場合、機能や操作面ではほぼ同一ですが画面の見た目が異なる場合があります。

Linux MintはISOイメージファイル形式（拡張子がiso）で提供されています。ここからは、ISOイメージのダウンロード、起動可能なメディアの作成、そしてコンピュータへのLinux Mintのインストール方法について説明します。

## 1章 USBメモリの準備（Windowsでの作業）

Linux Mintを使い始める準備として、Windowsパソコンで以下の作業を行います。

0. まずUSBフラッシュメモリ（以下USBメモリ）を用意
1. Linux Mint公式サイトからISOイメージをダウンロード
2. USBメモリ書き込みツールをインストール
3. USBメモリにISOイメージを書き込む

すべてWindows環境で完結する作業です。Linuxの知識は必要ありません。

> 本書ではUSBメモリでのインストールを前提に説明しています。DVDなどの光学メディアでも作成可能ですが、USBメモリの方が高速で手軽なためです。

OSインストールの各ステップ

### 1.1 ステップ0: USBフラッシュメモリを用意する

最も重要なことは「最新規格のUSBメモリを用意する」ことです。

長期間使っていなかった「古い規格のUSBフラッシュメモリ」は、書き込みや読み込み速度が遅く事前準備やインストールに長時間かかります。書き込みエラーが発生してインストール準備に失敗することもあります。

#### 1.1.1 推奨製品: KIOXIA TransMemory U301 USB 3.2 Gen1 32GB

なぜKIOXIA TransMemory
![なぜKIOXIA TransMemory](images/IG-23.jpg)

本書で推奨するのは、「KIOXIA（キオクシア）TransMemory U301 USBフラッシュメモリ 32GB」です。

| 項目 | 内容 |
|------|------|
| 製品名 | KIOXIA TransMemory U301 USBフラッシュメモリ 32GB |
| 型番 | KUC-3A032GW または KLU301A032GML |
| 規格 | USB 3.2 Gen1（USB 3.0 互換） |
| 価格 | 1,000円弱 |
| 入手先 | Amazon、ヨドバシカメラ、ほか家電量販店 |

必ず「USB 3.2」または「USB 3.0」と記載されているものを選んでください。同じKIOXIA TransMemoryシリーズでも、USB 2.0のモデルが存在します。形状は同じで印字のみ異なるので注意が必要です。

#### 1.1.2 なぜこのUSBメモリなのか

日本メーカーの信頼性: KIOXIAは旧東芝メモリから独立した日本のフラッシュメモリ専業メーカーです。NANDフラッシュメモリの発明元である東芝の技術を直接受け継いでおり、メモリの設計から製造まで日本国内で行われています。もちろんパッケージにも「日本製（Made in Japan）」と明記されています。

1年間のメーカー保証: キオクシア株式会社による1年間のメーカー保証付き。万が一の初期不良時にも国内サポート窓口で対応を受けられます。

入手性の高さ: Amazonでは月間200点以上の販売実績、5,000件を超えるレビューで星4.4の高評価。在庫切れが起きにくく必要なときにすぐ手に入ります。

コストパフォーマンス: 同等スペックのSanDisk製品が2,000〜3,000円台なのに対し、KIOXIA U301は約1,000円と大幅に安価です。

Linux環境での実績: KIOXIA（旧東芝メモリ）のUSBメモリは、Linuxコミュニティで長年にわたって広く使われてきた実績があります。起動時の認識やドライバ互換性のトラブル報告が極めて少なく、Linux初心者の方でも安心です。もちろん、Linuxのインストールに使用した後は、再フォーマットして高性能USBメモリとして長期間にわたり日常利用できます。（ファイル持ち運び用途なら 5〜10年）

#### 1.1.3 USBの規格と速度

USBメモリには世代ごとに転送速度の上限があります。

| 規格 | 最大速度 | Linux Mintインストール |
|------|---------|---------------------|
| USB 2.0 | 480 Mbps | × 非推奨（書き込み・起動とも極端に遅い） |
| USB 3.2 Gen1（推奨） | 5 Gbps | ◎ 快適 |
| USB 3.2 Gen2 | 10 Gbps | ◎（オーバースペック） |

USB 2.0とUSB 3.2 Gen1では、理論上の速度差は約10倍です。Linux Mintのインストールイメージは約2.8GBあるため、USB 2.0では書き込みに30分以上かかることもあります。USB 3.2 Gen1ならわずか数分で完了します。

> USB 3.2 Gen2 はオーバースペック: Gen2（10Gbps）対応モデルも存在しますが、USBメモリ内蔵のNANDフラッシュメモリ自体の速度がGen1の帯域で頭打ちになるため、Gen2を選んでも体感速度はほぼ変わりません。コストパフォーマンスを考えるとGen1で十分です。

### 1.6 USBメモリ書き込みツールをインストール

balenaEtcherの発音・語源・開発元
![balenaEtcherの発音・語源・開発元](images/IG-24.jpg)

ダウンロードしたISOファイルをUSBメモリに書き込むためのツールが必要です。本書では`balenaEtcher`を推奨します。

balenaEtcher 公式サイト: https://etcher.balena.io/

balenaEtcher 公式サイト
![balenaEtcher 公式サイト](images/W-34.jpg)

> 【コラム】balenaEtcher、どういう意味？
>ラズベリーパイなどで遊ぶときに、USBメモリにOSイメージを書き込むためによく使われるのがbalenaEtcher。読み方は「バレナ・エッチャー」です。後半の`Etcher`は「刻むもの」という意味。ガラスや金属に模様を彫る「エッチング」と同じ語源で、カードにOSを“刻み込む”道具、というまんまのネーミングです。問題は前半の`balena`。これ、イタリア語で「クジラ」なんです。
> 書き込みツールなのに、なぜクジラ？
>ヒントはソフトの世界の“推しキャラ”にあります。アプリを小さな箱（コンテナ）に詰めて動かすDockerという有名な技術があり、そのロゴが「背中にコンテナを積んだクジラ」。IT業界では「コンテナ＝クジラ」というイメージがすっかり定着しているんですね。balena社はこのDockerの仕組みを使って、世界中の小さな機器をまとめて動かすサービスを提供しているので、仲間のしるしとしてクジラを選んだというわけです。さらに、たくさんの機器を「群れ（fleet）」として管理するという意味でも、大海原を泳ぐクジラの群れのイメージはぴったり。次にOSイメージファイルを焼くときは、進捗バーの向こうでクジラがのんびり泳いでいる姿を、ちょっと想像してみてください。

ダウンロードページからWindows用のインストールプログラムをダウンロードします。

インストールプログラムをダウンロード
![インストールプログラムをダウンロード](images/W-35.jpg)

balenaEtcherのインストールが完了したらさっそく起動してみましょう。balenaEtcherはわずか3ステップ（ファイル選択 → USBメモリ選択 → 書き込み）で完了するシンプルなツールです。Windows、Mac、Linuxのすべてのプラットフォームに対応しています。残念ながら日本語版はありませんが、英語が苦手な方でも直感的に操作できるユーザーインターフェースになっています。

> テレメトリについての注意:
> balenaEtcherは利用状況をbalena社に送信する機能があります。プライバシーが気になる方はRufus（Windows専用、テレメトリなし、公式サイト: https://rufus.ie）をご利用ください。Linux Mintのインストールが完了すれば、インストールイメージを書き込んだUSBメモリは不要になります。再フォーマットしてデータ持ち運びなどの通常利用ができます。ここでもKIOXIA TransMemoryシリーズの高い信頼性と性能を生かすことができます。
>
> そもそも、OS（Windows）がMicrosoft社にテレメトリを送信しています。Windowsを使い続けている時点でデジタルプライバシーの大半は失われているので、書き込みツールのテレメトリに神経質になる必要はないでしょう。根本的なプライバシー対策のためにはLinuxOSへの移行を強くお勧めします。

### 1.7 ステップ6: USBメモリにISOイメージを書き込む

> 警告: USBメモリの中身はすべて消去されます。大切なデータが入っていないことを必ず確認してください。

ステップ0で準備した KIOXIA TransMemory U301をWindowsパソコンのUSBポート（青）に挿してください。

青いUSBポートは USB 3.0（正式には USB 3.2 Gen 1） で、データ転送が高速なポートです。色分けはメーカーの慣習で、ポート内部のプラスチック部分が青いものは USB 2.0 より約10倍速い規格を示します。

| 色 | 規格 | 転送速度 |
|---|---|---|
| 黒/白 | USB 2.0 | 480 Mbps |
| 青 | USB 3.0 (3.2 Gen 1) | 5 Gbps |
| 水色(ティール) | USB 3.1 Gen 2 (3.2 Gen 2) | 10 Gbps |
| 赤/オレンジ | 給電対応(常時通電) | 規格による |

外付けSSDやUSBメモリを挿すなら青いポートを選ぶと、ファイルコピーが体感でかなり速くなります。USB 2.0の機器を青ポートに挿しても問題なく動きますが、速度は機器側の上限（2.0）に合わせられます。

> まとめ: 青いUSBポートはUSB 3.0(5 Gbps)。USB 2.0の約10倍速く、外付けSSDやUSBメモリで効果を発揮する。

balenaEtcherを起動します。

### 4.1 EFI

#### 4.1.1 セキュアブート

EFIモードでLinux Mintをインストールした後、セキュアブート違反により起動できない場合は、以下のいずれかの解決策を試してください：

- インストールをやり直す：インストール前にインターネットに接続し、「グラフィックスおよびWi-Fiハードウェア、Flash、MP3などのサードパーティソフトウェアをインストールする」を選択しない。
- コンピュータのBIOS設定でセキュアブートを無効にする。

#### 4.1.2 EFI ブート順序

EFIモードでLinux Mintをインストールした後、コンピュータがブートメニューをスキップして直接Windows（または別のオペレーティングシステム）を起動する場合、ブート順序に問題がある可能性があります。

ブート順序を変更するには：

1. ライブモードでLinux Mintを起動します（USBメモリまたはDVDを使用）。
2. ターミナルを開きます。
3. `sudo efibootmgr`と入力して`Enter`を押します。

このコマンドは利用可能なブートオプションとブート順序を一覧表示します。

> BIOSモード（レガシー）でインストールしている場合
> `efibootmgr`はEFIブート専用のコマンドです。BIOSモードでインストールしたパソコンでは「EFI variables are not supported on this system」というエラーが表示されます。この場合は`os-prober`と`update-grub`、またはBIOS設定画面でブート順序を変更してください。

例として3つのブートオプションがあるとします：ubuntuが0000、linuxmintが0001、MacOS Xが0081。ブート順序先頭が0081の場合、コンピュータはMacOSのみを起動しようとし、Linux Mintを起動しようとしていないことを示します。

> 重要: 技術的な理由により、Linux MintはEFIブート名として`ubuntu`を使用しています。

ブート順序を修正するには、`sudo efibootmgr --bootorder XXXX,YYYY`（`XXXX`と`YYYY`は起動したいオペレーティングシステムのブートオプション）と入力します。

例：`sudo efibootmgr --bootorder 0000,0081`は、コンピュータにまずLinux Mint（`ubuntu`はLinux MintのEFIブート名）を起動し、次にMacOSを起動するよう指示します。

コンピュータを再起動します。

> 注意: 上記の例では`0000`が最初のブートオプションであるため、コンピュータはLinux Mintのgrubメニューで起動します。grubが失敗した場合（または`exit`コマンドで終了した場合）、コンピュータはブート順序に従い、MacOSに対応する`0081`の起動を試みます。

### 4.2 ブートオプション

一部のグラフィックカードやマザーボードは、Linux Mintにデフォルトで含まれるオープンソースドライバーとうまく動作しません。

#### 4.2.1 互換モード

最も簡単なオプションは、USBメモリ（またはDVD）のブートメニューから互換モードを選択することです。

#### 4.2.2 nomodesetブートオプション

互換モードが機能しない場合は、nomodesetブートオプションを試すことができます。

EFIモード： 「Start Linux Mint」オプションをハイライトして`e`を押し、ブートオプションを変更します。`quiet splash`を`nomodeset`に置き換えて`F10`を押して起動します。

BIOSモード： 「Start Linux Mint」をハイライトして`Tab`を押し、ブートオプションを変更します。`quiet splash`を`nomodeset`に置き換えて`Enter`を押して起動します。

インストール後もgrubブートメニューでこの操作を繰り返し、追加ドライバーをインストールするためにハードウェアドライバーの項を参照してください。

#### 4.2.3 その他のブートオプション

それでも起動できない場合は、以下のいずれかの解決策を試してください：

- `nomodeset`の代わりに`nouveau.noaccel=1`を試す。
- インストール後、ブートメニューから「詳細オプション → リカバリモード」を使用して「resume」を選択する。

#### 4.2.4 古いリリースのインストール

お使いのコンピュータが最新の Linux Mintリリースと互換性の問題がある場合は、同じLinux Mintシリーズの以前のリリースをインストールしてください。

例えば、Linux Mint18.3（4.10カーネル搭載）をインストールできない場合は、Linux Mint18（4.4カーネル搭載）をインストールして18.3にアップグレードしてください。

> 注意: 各シリーズの最初のリリースはLTS（長期サポート）カーネルを使用しています。このリリースからシリーズの最新版にアップグレードしても、カーネルは変更されません。

## 5章 よくある質問

### 5.1 マルチブート

> Windowsとのデュアルブート（マルチブート）について:
> Windows環境を残したまま Linux Mintをインストールする「マルチブート」も技術的には可能ですが、パーティション操作のミスなどでWindows側のデータを失うリスクがあります。本書ではデュアルブートは推奨しません。

#### 5.1.1 Windowsを常に先にインストールする

Windowsは他のオペレーティングシステムを検出せず、ブートメニューも提供しません。インストールするとブートシーケンスが上書きされコンピュータは直接Windowsで起動します。

Linux Mint（およびほとんどのLinuxディストリビューション）は他のオペレーティングシステムを検出し、どのシステムで起動するかを選択できるメニューを構築します。

このため、Windowsとデュアルブートまたはマルチブートしたい場合、「Linux Mintをインストールする前にWindowsをインストールすること」が重要です。

#### 5.1.2 ブートシーケンスの修復

Windowsがブートシーケンスを上書きした場合：

1. ライブモードでLinux Mintを起動します（USBメモリまたはDVDメディアを使用）。
2. ターミナルを開きます。
3. パーティションを一覧表示するには、`lsblk -f`と入力してEnterキーを押します。
4. Linux Mintがインストールされているパーティションを見つけます。ほとんどのシステムでは、唯一のext4パーティションです。

パーティションサイズを一覧表示するには`lsblk`を入力します。パーティションラベルを一覧表示するには`blkid`を入力します。

5. Linux Mintパーティションをマウントし、以下のコマンドでgrubメニューを再インストールします：

```bash
sudo mount /dev/sda4 /mnt
sudo grub-install --root-directory=/mnt /dev/sda
```

> 警告: 上記のコマンドでは、`/dev/sda4`と`/dev/sda`をお使いのLinux Mintパーティションとハードドライブデバイスの適切な名前に置き換えてください。

### 5.2 パーティション分割

#### 5.2.1 専用の/homeパーティション

Linux では、`/home`ディレクトリはユーザーデータと設定を保存するために使用されます。このディレクトリには各ユーザーアカウントに対するサブディレクトリが含まれます。例えば、ユーザー名が`john`の場合、ホームディレクトリは`/home/john`、ダウンロードは`/home/john/Downloads`、ドキュメントは`/home/john/Documents`、Firefoxのブックマークは`/home/john/.mozilla`のどこかにあります。

`/home`に専用のパーティションを割り当てることで、ユーザーデータをオペレーティングシステムの残りの部分から分離できます。利点は、ユーザーデータに影響を与えることなくオペレーティングシステムを消去して置き換えることができることです。

Linux Mintをインストールする際は？：

- `/`マウントポイントをオペレーティングシステム専用のパーティションに割り当て、インストールプログラムにフォーマットするよう指示します。
- `/home`マウントポイントをユーザーデータ専用のパーティションに割り当て、すでにユーザーデータが含まれている場合は、インストールプログラムにフォーマットしないよう指示してください。

> 警告: これは初心者ユーザーには推奨されません。インストール中のミスにより、すべてのデータが消去される可能性があります。常にバックアップを作成し、正しいパーティションを選択し、フォーマットオプションを慎重に確認してください。

> 注意: Linux Mintオペレーティングシステムは約15GBを使用し、追加のソフトウェアをインストールすると増加します。余裕があれば100GBを割り当ててください。空き容量のほとんどをホームパーティションに残してください。ユーザーデータ（ダウンロード、動画、画像）はより多くの容量を使用します。

Linux Mint 独自開発アプリの全史と技術背景
![Linux Mint 独自開発アプリの全史と技術背景](images/IG-36.jpg)

##### コラム: Linux Mint 独自開発アプリの全史と技術背景 Mintアイデンティティの源泉

Linux Mintがただの「Ubuntuの見た目違い」ではなく、独立したディストリビューションたり得ているのは、チームが20年近くにわたって独自アプリを作り続けてきたからです。この営為の本質は、創設者Clément Lefèbvre（Clem）が掲げた「Ubuntu, done right」という哲学に貫かれています。既存のものを置き換えるのではなく足りないものを補い、特定のデスクトップ環境に縛られない汎用部品を作り、上流GNOMEのような破壊的な変更からユーザー体験を守る。この三原則が、30以上のMint Toolsから始まる三世代のアプリ群を生みました。

2006年、当時のUbuntuは比較的使いやすいLinuxではあったものの、初心者には依然として壁が多くありました。システム更新の危険度を見分けにくく、ソフトのインストールは敷居が高く、メニューは見にくく、マルチメディアコーデックがありませんでした。Mintチームが最初に取った手段が、Pythonで書かれた一連のツール群です。`mintinstall`は初心者向けのアプリストア、`mintupdate`は安全度を1から5に分類して更新を可視化、`mintwelcome`は新規ユーザーをドライバやバックアップツールへ導く初回起動ガイドでした。これらは単なる機能追加ではなく、Mintというブランドの最初の触点であり、チームの価値観を具現化した設計でした。

しかし2011年、GNOMEプロジェクトが3.0をリリースした時、Mintチームの公式ヒストリーは当時を「catastrophe（大惨事）」と表現しました。パネル、トレイ、メニューといったUIが消失し、GTK3も初期段階で不安定でした。これは単なる技術的ショックではなく、Mintが自分たちのデスクトップ環境を掌握しなければならないという決定的な転機でした。二つの対応が取られました。一つはGNOME 2を引き継いだMATEプロジェクトへのコミット。もう一つはGNOME Shellをフォークして伝統的なパネル・メニュー型UIを再構築するCinnamonの開発です。Cinnamonは単一のアプリケーションではなくデスクトップ環境ですが、それがMintの決定的な分岐点となりました。上流から独立し、自分たちのビジョンを貫く覚悟。その後に続くすべての独自アプリ開発の源泉になったのです。

2016年、第二世代のX-Appsが登場します。GNOMEプロジェクトのテキストエディタgedit、PDFビューアEvince、画像ビューアEye of GNOME、メディアプレイヤーTotemといった主要アプリが、GNOME Shell専用のUIへ次々とリデザインされていく中で、Mintはこれらを自分たちで保守する道を選びました。手法は元プロジェクトの定期的な追従とバグ修正を継続しながら、ヘッダーバーに依存せず、Cinnamon・MATE・Xfceの三つのデスクトップ環境すべてで同じ見た目で動く、統一されたUIを貫くというものでした。その中核に位置するのが`libxapp`という共有ライブラリです。トレイアイコン、横断的なお気に入り機能、キーボード配列の切替、タスクバー連携。これらの共通機能を抽象化することで、複数のアプリが一貫した体験を提供します。`xed`、`xreader`、`xviewer`、`pix`といった主要アプリは今もMintの標準に含まれ、UbuntuのPPAでも利用可能です。

第三世代は2018年以降のアプリ群です。設計思想は単なる「既存アプリの保全」ではなく、「Linuxに欠けていたカテゴリそのものを埋める」ことにあります。Warpinatorはゼロから設計されたLANファイル転送ツールで、gRPCで通信し、Avahiでディスカバリを行い、コミュニティによってAndroid・Windows・macOSへまで移植されました。HypnotixはIPTVプレイヤーで、合法フリー番組のみを初期値とし、PythonとGTK3で実装されています。Web App Managerはウェブサイトをデスクトップアプリ化します。Timeshift（当初は外部開発）はシステム更新前の自動スナップショット機能を`mintupdate`に統合させ、ユーザーが危険な更新から自動的に回復できる体験を実装しました。

開発の中核はPython、C、Valaです。Mint ToolsはPythonで迅速な開発と修正を可能にし、X-AppsはCで書かれた高速性を確保しています。ビルドはMesonで統一され、Debianパッケージング形式で配布されます。翻訳はLaunchpadを通じたコミュニティ協力。GitHub上の`linuxmint/`organizationには150以上のリポジトリが整然と並びます。

重要なのは、MintのアプリがMintにだけ閉じていないという点です。CinnamonはFedora、Manjaro、openSUSEの公式Spinになりました。X-AppsはUbuntuで非公式PPAとして広く使われています。TimeshiftはManjaro、EndeavourOSの標準ツールになりました。Warpinatorはコミュニティ移植を通じてAndroid・Windowsに広がりました。

Linux Mintが「特別」である理由は、CanonicalやRed Hatのような大企業ではなく、Clemと数名のコアメンバー、そして多数のコントリビュータという小規模チームが、20年にわたってこれだけのアプリを一貫性を保ちながら維持し続けていることです。保守的なUI哲学によってエンドユーザーの体験を保護し、自社のCinnamonに閉じず他のデスクトップ環境にも貢献し、時には自社開発に固執せず優れた既存プロジェクトを柔軟に引き取る判断もする。それがMintのアイデンティティであり、単なるUbuntu派生ではなく、独立したデスクトップLinuxプロジェクトたり得させている源泉なのです。

## 17章 オフィススイート（LibreOffice）

LibreOffice vs Microsoft Office
![LibreOffice vs Microsoft Office](images/IG-08.jpg)

LibreOffice 自由なオフィススイートの全体像
![LibreOffice 自由なオフィススイートの全体像](images/IG-37.jpg)

##### コラム: LibreOffice 自由なオフィススイートの哲学と歴史

LibreOfficeはもともと2000年にSun Microsystemsが公開したOpenOffice.orgが起源です。2010年にOracleがSunを買収したことで、開発コミュニティが懸念を抱き、2010年9月にThe Document Foundation（TDF）が設立され、LibreOfficeは独立したオープンソースプロジェクトとしてフォークされました。TDFはドイツベルリンに本拠を置く非営利財団で、特定企業による買収を避けるため財団形態を採用しています。開発はTDF雇用の中核チーム、CollaboraやRed Hatなどのエコシステムパートナー企業、そして世界中の数百名規模のボランティアコントリビュータによって支えられています。

LibreOfficeは一つのインストールで6つのアプリケーションを提供します。Writer（ワープロ、Word対応）、Calc（表計算、Excel対応で500以上の関数を内蔵）、Impress（プレゼンテーション、PowerPoint対応）、Draw（ベクター図形描画でPDF編集も可能）、Base（データベース、Access対応）、Math（数式エディタ）です。すべて完全に無料で、広告やサブスクリプション、データ収集は一切ありません。

哲学面では、LibreOfficeはベンダーロックインからの自由を一貫して掲げています。標準ファイル形式はISO標準のOpenDocument Format（ODF）で、データはいかなるベンダー依存性も持たずに保存でき、10年後20年後も開ける長期アクセスが保証されます。これはMicrosoft 365やGoogle Workspaceのサブスクリプション・クラウド前提モデルに対する明確な対抗軸です。ライセンスはMPL 2.0とLGPLv3+のデュアルライセンスで、商用ソフトへの組み込みも容易になっています。

Microsoft Officeとの互換性は用途によって異なります。CalcとExcelの互換性は高く、数式やグラフはほぼ問題ありませんが、マクロ（VBA）は書き換えが必要です。WriterとWordは中〜高い互換性を持ちますが、段落間スペースやフォント置換で微妙な差が生じます。ImpressとPowerPoint、DrawとVisioはやや互換性が落ち、アニメーションやSmartArtで崩れやすいです。崩れの主要因はMicrosoftフォント（メイリオ、游ゴシック、Calibri等）の不在、段落・行間計算式の相違、マクロの方言的差異です。実用的な対処法として、最終配布をPDFにすることが事実上の解決策となります。

ユーザーインターフェースは柔軟で、従来型のメニュー＋ツールバー、Microsoft Office風のリボンUI、タブ付きコンパクト、グループバー、コンテキストシングルなど複数のモードから選択可能です。24.2以降ではOSのダークテーマに自動追従するダークモード機能も搭載されています。拡張機能も豊富で、公式ストアから多数の拡張を入手でき、Python、Java、JavaScriptなど複数のスクリプト言語に対応しています。

バージョン体系は2024年2月の24.2から、西暦下2桁と月を組み合わせた形式（24.2、24.8、25.2…）に変更されました。Fresh（最新版、年2回）とStill（安定版、前世代のメジャーバージョン）の二系統が並行提供されています。Linux Mintには標準でLibreOfficeが同梱されており、より新しいFresh版が必要な場合はPPA経由でのインストール、Flatpak、公式サイトからのDEBパッケージといった複数の選択肢が用意されています。Linux MintにLibreOfficeが標準搭載されている理由は、オープンソース思想との親和性、完全な無料性、Linuxネイティブな安定性、そしてOfficeファイル互換性による実用性が、完璧にそろった製品だからです。

### 19.8 Warpinator（ネットワークファイル転送）

Warpinator LAN経由でファイルを送受信するツール
![Warpinator LAN経由でファイルを送受信するツール](images/IG-27.jpg)

Warpinator は Linux Mintチームが開発した、ローカルネットワーク経由で安全にファイルを転送できるアプリです。同じ Wi-Fi に接続している端末同士で、インターネットを経由せずに直接ファイルをやり取りできます。

クラウドストレージにアップロードしたり、USBメモリで持ち歩いたりする手間が不要で、写真や動画、文書を簡単に転送できます。Linux 同士はもちろん、Windows、Mac、Android にも対応する非公式クライアントが存在します。

Warpinator の特徴:

- ローカルネットワーク内で完結（インターネット不要）
- 暗号化通信
- ファイルサイズ制限なし
- インストール不要（Linux Mintに標準搭載）
- クロスプラットフォーム対応

#### 19.8.1 偽サイトに関する重要警告

警告: warpinator.com は公式とは無関係の偽サイトであり、悪意のあるソフトウェアが含まれている可能性があります。絶対にこのサイトからダウンロードしないでください。Linux Mintチームが何度も削除を試みていますが、ホスティング会社が対応していないため放置されています。

公式ソースは以下のリポジトリのみです:

- 公式リポジトリ: https://github.com/linuxmint/warpinator

他プラットフォーム版（非公式）の入手先:

| プラットフォーム | リンク |
|---|---|
| Android | https://github.com/slowscript/warpinator-android |
| Windows | https://github.com/slowscript/warpinator-windows |
| Windows | https://winpinator.swisz.cz |

Linux Mintには最初から搭載されているので、Linux Mintユーザーは追加でダウンロードする必要はありません。

#### 19.8.2 グループコードのカスタマイズ（必須）

Warpinator はローカルネットワーク上で「グループコード」を使ってデバイス同士を識別します。デフォルトでは「Warpinator」という共通のコードが設定されているため、同じネットワークの誰でも接続できてしまいます。

セキュアモードを有効にするには、グループコードをユニークなものに変更するだけです。すべての接続したいデバイスで同じ（変更後の）コードを設定します。8文字以上32文字以下の英数字を推奨します。

セキュアモードが有効になるまでは、以下の制限が適用されます:

- ログイン時の自動起動が無効
- すべての受信転送にユーザー承認が必要
- Warpinator は60分後に自動終了

つまり、グループコードを変更するまでは Warpinator は本格運用できない設計になっています。安全のためによく考えられた仕組みです。

#### 19.8.3 ファイアウォール設定

Warpinator が使用するポートをファイアウォールで開放する必要があります:

- 転送用ポート: 42000（TCP）
- 認証用ポート: 42001（TCP）
- Flatpak版同士の接続: UDP ポート 5353

gufw を使っている場合、Warpinator が自動的にルールを追加できます（Flatpak版を除く）。

#### 19.8.4 接続できないとき

Warpinator が他のデバイスを認識しない場合、以下を確認してください。

- すべてのデバイスが同じ Wi-Fi（同じサブネット）に接続されているか
- グループコードがすべてのデバイスで一致しているか
- VPN が有効になっていないか（一時的に無効化して試す）
- ファイアウォールで Warpinator のポートが開放されているか
- ルーターが「クライアント間通信を遮断する」設定になっていないか（ホテルや公共 Wi-Fi でよくある）

仮想マシンで使う場合は、ネットワークアダプターを「NAT」ではなく「ブリッジ」に設定してください。

> Warpinator は mDNS（Multicast DNS）を使って同じネットワーク上のデバイスを検出するため、ネットワーク構成やセキュリティ設定によっては認識されないことがあります。上記のポイントを確認しても接続できない場合は、ネットワーク管理者に相談するか、別のファイル転送方法を検討してください。

### 19.7 LocalSend ― iOS/iPadOSも含む横断ファイル転送

Warpinatorの最大の欠点はiOS/iPadOSに対応していないことです。iPhoneやiPadとファイルをやり取りする場合は、代替手段として **LocalSend** を検討してください。Windows、macOS、Linux、Android、iOS、iPadOSすべてに対応した、オープンソースのクロスプラットフォーム転送ツールです。

LocalSend ― クロスプラットフォームのファイル転送
![LocalSend ― クロスプラットフォームのファイル転送](images/IG-28.jpg)

#### LocalSendの主な特徴

- **対応OS**: Windows / macOS / Linux / Android / iOS / iPadOS（Warpinatorに無いiOSサポート）
- **動作原理**: ローカルネットワーク上で完結（インターネット不要）


または公式サイト（localsend.org）から DEB / AppImage を入手します。Warpinator と併用しても干渉しません。

### 38.1 マイナーアップグレード

| 元のバージョン | 先のバージョン | タイプ |
|-------------|-------------|--------|

| 21, 21.1, 21.2 → | 22.3 | マイナー |
| 21.3 → | 21 | メジャー |

### 41.2 サウンドの問題

Linux Mint Xfce 22.x（22.3を含む）では PulseAudio が標準のサウンドサーバーとして採用されています（CinnamonエディションではPipewireへの移行が進んでいますが、Xfceエディションでは現状PulseAudioが既定です）。

#### 41.2.1 現在のサウンドサーバーの確認
```bash
inxi -A
```

`Server: PulseAudio` と表示されれば標準構成です。`pipewire-pulse` と表示される場合はPipewireが入っています。

#### 41.2.2 Pipewireへの切り替え（任意）

PulseAudioで音が出ない、または最新のサウンドサーバーを使いたい場合はPipewireに切り替えられます。

```bash
sudo apt install pipewire pipewire-pulse
sudo reboot
```

### 41.3 タッチパッドの問題

デフォルトドライバーは `libinput` です。問題がある場合は `synaptics` に切り替えられます。

## 44章 WINE（Windows互換レイヤー）

WINE Windows互換レイヤーの仕組み
![WINE Windows互換レイヤーの仕組み](images/IG-31.jpg)

### 44.1 概要

WINEは、WindowsアプリケーションをLinuxやmacOS等のPOSIX互換環境で実行するための互換レイヤーです。その名称は「Wine Is Not an Emulator」の再帰的頭字語であり、CPUエミュレータや仮想マシンではなく、Windows APIの呼び出しをネイティブのPOSIX呼び出しへ実行時に翻訳する仕組みです。この設計によりエミュレーションや仮想化に伴う性能ペナルティを回避しています。

1993年にBob AmstadtとEric Younqdaleによって発足したWINEプロジェクトは、1994年からAlexandre Julliardが開発リーダーを務めています。初期は16ビットWindows 3.xをターゲットにしていましたが、32ビット、64ビットへと段階的にシフトしました。2008年にバージョン1.0に到達し、その後も継続的に進化しており、2026年1月にはWine 11.0が安定版としてリリースされています。

技術的には、WINEはユーザー空間でWindows ABIを完全に実装するアプローチを採用しており、`ntdll.dll`や`kernel32.dll`といった主要なWindows DLLをLGPLの下でゼロから再実装しています。`wineserver`はWindowsカーネルが提供する基本機能を担当する常駐デーモンで、同期オブジェクト、プロセス間通信、レジストリ、シグナル処理などを管理します。DirectX対応については`WineD3D`がDirect3DをOpenGLに変換し、最新のDirect3D 12に対応するために`vkd3d`やDXVKなどのサブプロジェクトが開発されています。

### 44.2 インストール

Linux Mint Xfce 22.xでは標準でプリインストールされていないため、明示的に導入する必要があります。最も簡単なのは公式リポジトリからのインストールです。

```bash
sudo apt install wine wine32 winetricks
```

より新しい版が必要な場合は、WineHQ公式リポジトリを追加してインストールします。

```bash
sudo dpkg --add-architecture i386
sudo mkdir -pm755 /etc/apt/keyrings
sudo wget -O /etc/apt/keyrings/winehq-archive.key https://dl.winehq.org/wine-builds/winehq.key
sudo wget -NP /etc/apt/sources.list.d/ https://dl.winehq.org/wine-builds/ubuntu/dists/noble/winehq-noble.sources
sudo apt update
sudo apt install --install-recommends winehq-stable
```

### 44.3 基本的な使い方

インストール後は、`wine`コマンドでWindowsアプリケーションを実行できます。

```bash
wine setup.exe
```

`winecfg`ツールで互換性設定を調整できます。`winetricks`スクリプトを使用すれば、不足しがちなMicrosoft DLL、フォント、VC++ランタイム、DirectXなどの依存ソフトウェアを一括で導入できます。

Windowsのドライブは `~/.wine/drive_c/` にマップされます。`.exe`ファイルを右クリックして「WINEで開く」を選択することでも実行可能です。

### 44.4 主な利用ケースとエコシステム

WINEの主要な利用ケースには、古いWindowsゲームやレガシーなWindows専用業務アプリケーション、社内向けツールの実行などが含まれます。Windows互換性データベース（AppDB）では、アプリケーションごとに動作可能性が5段階（Platinum/Gold/Silver/Bronze/Garbage）で評価されています。

WINEの周辺エコシステムは充実しており、CodeWeaversの商用ソリューション`CrossOver`はWINEをベースにした支援版です。Valveの`Proton`はSteam Playに統合されており、Linuxでのゲーミング体験を大幅に改善しました。`Lutris`は複数のランタイムを一元管理するゲーミングランチャで、`Bottles`はGTK4ベースのモダンなPrefix管理GUIを提供します。2024年にMicrosoftが.NET Frameworkの再実装である`Mono`プロジェクトをWINEチームに移譲したことで、.NET互換性が大きく前進しており、WINEエコシステムは企業レベルでの協業が進行中です。

## 45章 Flatpakの管理

Flatpak ユニバーサルパッケージシステム
![Flatpak ユニバーサルパッケージシステム](images/IG-32.jpg)

### 45.1 概要 ディストリビューション非依存のアプリ配布

Flatpakはディストリビューション非依存のアプリケーション配布・パッケージ管理システムであり、Bubblewrapというサンドボックス技術とOSTreeという差分配信システムを組み合わせることで、Linux各ディストリ間での統一的なアプリ実行環境を実現しています。Red Hatの開発者Alexander Larsson氏による2015年の実装当初は`xdg-app`と呼ばれ、2016年に現在の名称に改称されました。現在はFlatpakコミュニティの標準リポジトリFlathubを中心に、Fedora、Linux Mint、elementary OSなど38以上のディストリビューションで採用されている成熟したプラットフォームです。

Flatpakの技術的な核となるのは、BubblewrapによるLinuxユーザー名前空間を活用した軽量サンドボックス隔離と、OSTreeによるGit風のオブジェクトストアを用いた効率的な差分配信です。アプリケーションは独立した`org.freedesktop.Platform`や`org.gnome.Platform`といった共有ランタイムに依存することで、ホストOSの共有ライブラリとは切り離された環境で動作します。ユーザーの設定ファイルはサンドボックス内の`~/.var/app/<app-id>/`にマップされ、ホームディレクトリへ漏れない構造になっています。権限管理は`finish-args`という宣言型のパーミッションで制御され、ユーザーは`flatpak override`コマンドやFlatsealというGUIツールで事後的に権限を調整できます。`xdg-desktop-portal`という仲介層により、サンドボックス内のアプリはファイル選択ダイアログや通知などのホスト機能にD-Bus経由で安全にアクセスします。

### 45.2 aptパッケージとの違い、SnapやAppImageとの比較

従来のaptやdebパッケージは特定のディストリビューションとそのライブラリバージョンに密結合するため、アプリ開発者は複数ディストリ向けのパッケージングとテストが必要となり、OSアップグレード時にアプリが動作しなくなるリスクを抱えていました。これに対しFlatpakは単一のビルドで全ディストリ対応を実現し、開発者が直接ユーザーに更新を配信でき、権限の最小化によるセキュリティと使い勝手のバランスを取ります。

SnapはCanonicalが主導する中央集権的なSnap Storeを用いており、AppImageは配布形式に過ぎずサンドボックスや差分更新がない点でFlatpakと異なります。実用的な住み分けとして、デスクトップGUIアプリはFlatpak、システムサービスやサーバ用途はSnapやOSネイティブパッケージが適切とされています。

Flatpakの主な利点は、真のディストリ独立性、共有ランタイムによるABI安定性、既定で隔離された権限分離、OSTreeによる効率的な差分更新、管理者権限不要なユーザー単位インストール、安定版とベータ版の複数バージョン共存です。初回ダウンロード時はランタイム取得で容量が大きいという批判がありますが、OSTreeのファイルレベル重複排除により二本目以降は急速に効率化されます。テーマやフォントが反映されないという課題もGTK・Qtのテーマランタイム拡張整備で大幅改善され、Flatsealによる権限の可視化と調整でセキュリティの懸念にも応答しています。

### 45.3 Linux Mintでの利用

Linux MintではFlatpakがデフォルトでサポートされており、Flathubリポジトリが有効化されています。ソフトウェアマネージャー（mintinstall）にはネイティブにFlatpakが統合されており、ユーザーは通常のGUIから`flatpak install`コマンド相当の操作でアプリをインストール可能です。

### 45.2 コマンドラインでの操作
```bash
# アプリケーションの検索
flatpak search アプリ名

# アプリケーションのインストール
flatpak install flathub アプリケーションID

# インストール済みアプリの一覧
flatpak list

# アプリケーションのアップデート
flatpak update

# アプリケーションの削除
flatpak uninstall アプリケーションID
```

## 47章 一般的な概念

### 48.1 観察（Observation）

コンピュータを使用していて、突然何かおかしいことに気づくことがあります。何かが正しく動作していないように見えます…期待どおりに動作しません。

ハードウェアに問題があるのでしょうか、それともソフトウェアに問題があるのでしょうか？設定やコンピュータの使い方に問題があるのでしょうか？間違った結果を期待しているのでしょうか？

まだわかりませんが、一つ確かなことがあります：見たものが期待と一致しませんでした。

この段階では、これは観察です。何かがおかしいように見えるので、トラブルシューティングを開始します。

> 注意: 観察の例を示します：「歩いている時に右足に痛みを感じた。」

> 重要: 観察をバグとして報告しないでください。観察はバグではなく、観察です。観察がバグの発見につながる可能性があると思う場合は、確認するためにトラブルシューティングを行ってください。

### 48.2 期待（Expectation）

観察とは、コンピュータが行うことと、あなたが期待していることとの不一致です。

トラブルシューティングの前に、あなたの期待が正しいことを確認してください。関連するドキュメントを読み、関連する問題をウェブで検索し、リリースノートに目を通し、それでもわからない場合はコミュニティで質問してください。

これを行わずにトラブルシューティングを行うことはできません。

あなたの期待が確かに正しければ、トラブルシューティングを続けてください。

> 注意: 有効な期待の例を示します：「靴が足を痛めるべきではない。」

### 48.3 再現性（Reproducibility）

トラブルシューティングにおける重要なステップは再現性です。目標は、問題を引き起こす方法を特定することです。

一連の手順を何度も繰り返し実行でき、常に同じ問題が観察される場合、その問題は再現可能であり、トラブルシューティングに成功する可能性が高くなります。

> 注意: 再現可能な問題の例を示します：「歩くたびに右足に痛みを感じる。」

再現性はトラブルシューティングの鍵です。再現できない問題を分析することは非常に困難です。問題を引き起こすための手順を特定できなければ、問題のトラブルシューティングに成功する可能性は低いでしょう。

ヘルプを求めたりバグを報告したりするとき、人々は常に問題が再現可能かどうか、そしてそれを再現するために実行する手順は何かを尋ねます。

問題が一度だけ発生してもう発生しない場合、または時々発生するがなぜかわからない場合…あなたはまだこれらの手順を特定できていません。

> 重要: 再現できない問題のバグ報告を行わないでください。バグ報告時には、問題を再現するための手順も必ず記載してください。

### 48.4 責任の特定（Responsibility）

トラブルシューティングにおける重要なステップは責任の特定です。この段階では、すでに以下のことが確立されています：

- 観察：コンピュータが期待どおりに動作しない。
- 期待：あなたの期待は正しい。
- 再現性：問題を再現でき、そのための手順を特定している。

ここでの目標は、問題の原因となっているコンポーネントを特定することです。

これを見つけるための最良の方法は、消去法で進めることです。再現性の段階で問題を再現するために必要な一連の手順を特定しました。ここで手順の数を減らし、問題に関与している可能性のあるコンポーネントを除外して、実際にどのコンポーネントが原因かを特定する必要があります。

いくつかの例を示します：

- アプリケーションがロシア語で実行すると異常終了する…英語でも異常終了しますか？
- コンピュータの起動が遅い…オフラインの時も遅いですか？USB デバイスが接続されていますか？
- デスクトップがフリーズする…デフォルト設定でも発生しますか？サードパーティのアプレットなしでも発生しますか？

責任のあるコンポーネントを特定するもう一つの戦略は、異なる環境で問題を再現してみることです。

いくつかの例を示します：

- Cinnamon で問題が見られる場合、MATE でも発生しますか？
- 特定のリリースで問題が見られる場合、以前のリリースでも発生しますか？
- Linux Mintで問題が見られる場合、Ubuntu でも発生しますか？

共通点と相違点を特定することで、問題がどこにあるかを特定できる可能性が高まります。

> 注意: 責任のあるコンポーネントが特定された問題の例を示します：「私の Nike の靴は歩くたびに右足を痛めます。他の靴では痛みを感じません。同じ靴下、同じ場所、同じ時間でも同様です。」

この段階では、問題の原因を理解するのに十分な情報はまだありませんが、問題の原因となっているコンポーネントの特定には成功しています。

> 重要: Linux Mintは数千のソフトウェアコンポーネントから構成されており、その多くは非常に異なるチームによって開発されています。適切なコンポーネントを特定することは、どの開発チームが支援できるか、そしてどこに問題を報告すべきかを知るための鍵です。

### 48.5 変更（Change）

以前は動作していたものが動作しなくなった場合、トラブルシューティングの重要な側面は変更です。

最近何が変わりましたか？何か新しいものをインストールしましたか？アップデートを適用しましたか？設定を変更しましたか？別の場所から接続していますか？

物事が動作していた時と動作しなくなった時のコンテキストの違いを確認することが鍵であり、責任の特定（つまり問題の原因となっているコンポーネント）を非常に迅速に行うのに役立ちます。

> 注意: 変更が鍵となる問題の例を示します：「私の Nike の靴が右足を痛めます。洗濯機に入れるまでは問題ありませんでした。」

### 48.6 エラー（Errors）

多くの場合、コンピュータは問題を検出してエラーメッセージを報告します。エラーメッセージを常に読んで理解するようにしてください。多くの場合、問題の原因を説明しており、回避策や解決策を提案してくれることもあります。

#### 47.6.1 システムログ

システムログには、クラッシュ、ハードウェア、ドライバー、ネットワークの問題に関する手がかりが含まれていることがよくあります。以下を使用してシステムログを確認できます：

- システムログツール（アプリケーションメニューから）
- `dmesg` コマンド
- `journalctl` コマンド
- `/var/log/syslog` ファイル

#### 47.6.2 セッションエラー

ログインできない場合やデスクトップ環境に関する問題の場合は、`~/.xsession-errors` ファイルと `/var/log/lightdm/` ディレクトリのログファイルを確認してください。

#### 47.6.3 アプリケーション出力

アプリケーションが正しく動作しない場合は、アプリケーションを閉じてターミナルから実行してください。ターミナルにエラーメッセージが出力され、問題の原因に関する手がかりが得られる場合があります。

#### 47.6.4 クラッシュ

クラッシュ後、メニュー → システムレポート を起動して、クラッシュに関する情報とスタックトレースを確認できます。この情報は開発者にとって貴重であり、クラッシュの原因を理解しようとする際に非常に役立ちます。

> 重要: バグを報告する際は、常にエラーを探し、必ず報告してください。

### 48.7 環境（Environment）

あなたの設定、ロケール、インストールしたアプリケーションのセット、そしてコンピュータを他の人のものとユニークまたはやや異なるものにしているすべてのものを、環境と呼びます。

問題があなたのコンピュータでは常に再現可能だが、まったく同じ手順で他のコンピュータでは発生しない場合、環境が鍵であり、2台のコンピュータの環境の違いを確認する必要があります。

> 重要: 他の人があなたが提供した手順で問題を再現できない場合は、環境に関するより多くの情報を提供してください。

問題の性質に応じて、環境のさまざまな部分を確認する必要があるかもしれません。

#### 47.7.1 ロケール

ロケールは、言語と地域の設定で構成されます。ロケールに関連する一般的な問題をいくつか挙げます：

- 不正な翻訳によるクラッシュ。
- 翻訳の欠落。
- Unicode 文字によるクラッシュ。
- 長い翻訳によるウィジェットやアプリケーションの幅の問題。
- 特殊文字の表示失敗。

問題がロケール固有のものである場合は、言語を英語に設定し、ログアウトして再度ログインして、問題がまだ発生するかどうかを確認してください。

ロケールの詳細を表示または共有するには、ターミナルを開いて `locale` と入力します。

#### 47.7.2 パッケージリスト

パッケージやライブラリの不足により問題が発生する場合があります。ターミナルを使用して検索できます。例えば、foobar ライブラリを検索するには、`apt search foobar` と入力します。

システムにインストールされたパッケージのリストを表示または共有するには、`dpkg -l` と入力します。

特定のパッケージのバージョンを確認することもできます。例えば、cinnamon のインストール済みバージョンと利用可能なバージョンを確認するには、`apt policy cinnamon` と入力できます。

最後に、`inxi -r` でリポジトリを一覧表示できます。

## 48章 バグの報告

### 49.1 なぜ報告するのか（Why）

バグが報告される理由は明白に思えるかもしれませんが、正しく理解することが非常に重要です。

バグ報告は、バグの修正や改善につながる場合にのみ価値があります。オープンなバグ報告のうち、実際にそうなるのはごくわずかです。

ソフトウェアが迅速に改善されるためには、開発チームは修正につながる可能性が最も高いバグ報告を特定し、それに取り組む必要があります。

理想的には、開発チームはすべてのオープンなバグ報告を把握し、ソフトウェアの品質を最も向上させる可能性のあるものに取り組むべきです。しかしオープンソースでは、チームが小さくコミュニティが巨大であるため、オープンなバグ報告の数は通常非常に多く、チームはすべてのオープンなバグ報告を読み、処理し、把握することができません。10件程度のレポートがある小さなプロジェクトでは問題ありませんが、数千件のオープンなバグ報告がある大きなプロジェクトでは確実に問題です。

バグ報告の作成者は問題に苦しんでおり、開発チームがそれを再現できるかどうか、チームがどう考えるかに関わらず、問題は現実のものだと考えています。バグ報告がクローズされると、作成者はそれを受け入れるのが難しいと感じるかもしれません。フラストレーション、正当性、恩知らず、無視されたという感情が働くことがあります。

そのような場合は個人的な感情を脇に置き、効率的であることに集中することが本当に重要です。バグを報告する際、あなたと開発チームの両方がたった一つのことに集中しています：ソフトウェアの改善です。

開発者はあなたが彼らの仕事を楽しんでいることをすでに知っており、あなたも彼らがあなたのフィードバックを大切にしていることを知っています。問題はあなたの問題が本物かどうか、人々がどう感じるかではなく、このバグ報告を迅速に成功するバグ修正に変えることができるかどうかです。できないのであれば、クローズすべきです。

> 重要: バグを報告する理由は、ソフトウェアの問題（または問題かもしれないもの）を文書化したりカタログ化したりすることではなく、ソフトウェアを改善することです。成功するバグ修正につながらないバグ報告は邪魔になり、開発者がつながるバグ報告を迅速に特定することを妨げます。バグ報告の目標はソフトウェアを改善することです。バグ報告を提出する際は、それが正当かどうかではなく、バグ修正につながるほど適切で、シンプルで、完全であるかどうかを自問してください。

### 49.2 いつ報告するのか（When）

トラブルシューティングが完了する前にバグ報告を開かないでください。

あるプロジェクトに開発者が 2 人、オープンなバグ報告が 100 件、フォーラムと IRC のアクティブユーザーが 1,000 人、全体で 100 万人のユーザーがいるかもしれません。

まずできる限り自分で問題のトラブルシューティングを行い、次にコミュニティの他のユーザーの助けを借りてから、開発チームとやり取りすべきです。

以下のすべての条件が満たされた場合にバグを報告すべきです：

- バグであることが絶対に確かである（再現性、責任を確立し、原因を特定している）。
- チームが取り組むのに十分な情報を収集している（エラーメッセージ、再現手順など）、そしてそれが迅速に修正につながることを確信している。
- 問題がまだ報告されていない。

> 重要: 開発者は質問、トラブルシューティング、分析を手伝うことができますが、開発者は非常に少なく、他にも多くのオープンなバグ報告があります。開発者が最も得意とすること、すなわち物事を修正することに活用してください。すべてが完了した時（観察、トラブルシューティング、分析、情報収集、原因の理解）、足りないのは実際の修正だけという段階でのみバグ報告を開くべきです。開発者に分析やトラブルシューティングを依頼しないでください。あなたが理解できないバグは、開発者が一晩で修正するバグにはなりにくいでしょう。

### 49.3 何を報告するのか（What）

一般化するのは難しく、常に特殊なケースがあります。理想的には、報告すべきものは実際のバグ、すなわち決定論的で、理解され、分析され、したがって修正可能な問題です。

> 注意: 観察を報告しないでください。観察は開発者にとってほとんど役に立たず、役に立つ場合でも改善に変えるには通常大量の時間と労力を必要とします。

### 49.4 どこに報告するのか（Where）

Linux Mintオペレーティングシステムは数千のソフトウェアコンポーネントから構成されています。問題の原因となっているコンポーネントを特定したら、それを誰がメンテナンスしているかを特定する必要があります。

#### 48.4.1 Mint コンポーネントとアップストリームコンポーネント

Linux Mint内のコンポーネントには 2 種類あります：

- Mint コンポーネント は Linux Mintによってメンテナンスまたはパッチが適用されています。
- アップストリームコンポーネント は Ubuntu（LMDE の場合は Debian）によってメンテナンスされています。

ターミナルを使用して特定のコンポーネントに関する情報を取得できます。

`apt contains` を使用して、特定のファイルを含むパッケージの名前を見つけます。例えば、`/usr/share/polkit-1/actions/org.gnome.gnome-system-monitor.policy` ファイルの問題を追跡している場合は、以下のように入力できます：
```bash
apt contains /usr/share/polkit-1/actions/org.gnome.gnome-system-monitor.policy
```
```
gnome-system-monitor: /usr/share/polkit-1/actions/org.gnome.gnome-system-monitor.policy
```

出力は、このファイルが gnome-system-monitor パッケージの一部であることを示しています。

パッケージ名がわかったら、`apt policy` を使用して誰がメンテナンスしているかを確認できます：
```bash
apt policy gnome-system-monitor
```
```
gnome-system-monitor:
  Installed: 3.18.2-1ubuntu1
  Candidate: 3.18.2-1ubuntu1
  Version table:
 * 3.18.2-1ubuntu1 500
        500 http://archive.ubuntu.com/ubuntu xenial-updates/main amd64 Packages
        100 /var/lib/dpkg/status
     3.18.2-1 500
        500 http://archive.ubuntu.com/ubuntu xenial/main amd64 Packages
```

上記のように、gnome-system-monitor は Ubuntu リポジトリからのもので、したがってアップストリームコンポーネントです。関連するバグは Ubuntu に報告すべきです。

もう一つの例を示します：
```bash
apt policy gnome-calculator
```
```
gnome-calculator:
  Installed: 1:3.18.3-0ubuntu1.16.04.1.mint1
  Candidate: 1:3.18.3-0ubuntu1.16.04.1.mint1
  Version table:
 * 1:3.18.3-0ubuntu1.16.04.1.mint1 700
        700 http://packages.linuxmint.com sylvia/upstream amd64 Packages
        100 /var/lib/dpkg/status
     1:3.18.3-0ubuntu1.16.04.1 500
        500 http://archive.ubuntu.com/ubuntu xenial-updates/main amd64 Packages
     1:3.18.3-0ubuntu1 500
        500 http://archive.ubuntu.com/ubuntu xenial/main amd64 Packages
```

今回は gnome-calculator を見ています。上記のように、Linux Mintはバージョン `1:3.18.3-0ubuntu1.16.04.1.mint1` を提供しており、それがインストールされているバージョンです。この例では、gnome-calculator のバージョンは Mint コンポーネントであり、関連するバグは Linux Mintに報告すべきです。

#### 48.4.2 アップストリームバグ：Launchpad と Debbugs

バグが Ubuntu コンポーネントに関連する場合は、Launchpad で報告すべきです。

バグが Debian コンポーネントに関連する場合は、Debian のバグ追跡システムで報告すべきです。

> 重要: Ubuntu や Debian にアップストリームバグを報告する前に、Ubuntu や Debian で問題が再現可能であることを常に確認すべきです。仮想マシンに Ubuntu（または Debian）をインストールして、問題の再現を試みてください。問題が Linux Mint固有のものであれば、コンポーネントがアップストリームであるかどうかに関わらず、Linux Mintに直接報告すべきです。

#### 48.4.3 MATE バグ：Github/mate-desktop

MATE は Linux Mintと共同開発されています。MATE またはそのコンポーネントの 1 つに影響するバグは、MATE の Github サイトで報告すべきです。

これの例外は Linux Mint固有のバグです。例えば、バグが mintmenu、mintdesktop、または MATE の Mint テーマに関連する場合は、Linux Mintに直接報告してください。

#### 48.4.4 Cinnamon、X-Apps、Linux Mintのバグ

Linux Mintには 3 つの開発チームがあります：

- Cinnamon 開発チーム は、nemo と muffin を含むすべての Cinnamon コンポーネントをメンテナンスしています。
- X-App 開発チーム は、X-App アプリケーション（pix、xed、xreader、xplayer、xviewer）、ライブラリ、slick-greeter、blueberry などのすべてのクロスディストリビューションプロジェクトをメンテナンスしています。
- Linux Mint開発チーム は、すべての Mint ツールおよび Mint リポジトリを通じて配布されるその他のコンポーネントをメンテナンスしています。

これらのチームにバグを報告する際は、Linux Mintの Github サイトでコンポーネントを見つけてください。例えば、nemo のバグは Nemo に、mintmenu のバグは Mintmenu に、xplayer のバグは Xplayer に報告すべきです。

Cinnamon に関する一般的な問題を報告したい場合は、Cinnamon を使用できます。

Linux Mintに関する一般的な問題、Linux Mintがパッチを適用したアップストリームコンポーネントに関する問題、または Linux Mint固有のアップストリームコンポーネントに関する問題を報告したい場合は、Linux Mintを使用できます。

### 49.5 どのように報告するのか（How）

#### 48.5.1 正確で関連性のある情報を提供する

開発者がまず行おうとするのは、問題の再現方法を理解することです。常に関連情報を提供してください：

- コンピュータで問題を常に再現するために実行する手順（できるだけ正確に）。
- 開発者の環境と異なる可能性のある、あなたの環境の特殊性（Mint のエディションとリリース、ロケール、ドライバーなど）。
- 関連するエラーメッセージやソフトウェアの出力。
- 問題を示すスクリーンショット。
- 開発者が問題を理解したり再現したりするのを容易にするあらゆるもの。

> 注意: 環境に関する多くの情報は `inxi -Fxxrzc0` コマンドで一覧表示できます。

#### 48.5.2 クラッシュのスタックトレースを提供する

クラッシュを報告する際は、以下を提供してください：

- クラッシュの dmesg 行。
- クラッシュのスタックトレース（メニュー → システムレポート で取得できます）。
- 他のバグと同様に、問題を再現する手順。

#### 48.5.3 期待を説明する

馬鹿げているように聞こえるかもしれませんが、ソフトウェアが何をするかは明確でも、作成者が何を期待しているかが明確でないバグ報告があることがあります。これは誤解につながる可能性があります。

可能であれば、ソフトウェアの動作がなぜ間違っていると思うか、代わりに何をすることを期待するかを簡潔に説明してください。

#### 48.5.4 忍耐強く、愉快であること

ほとんどの人はそうしています。インターネット上では不機嫌になりやすい（または単に不機嫌に「聞こえる」だけかもしれません）。開発者もユーザーも、やり取りをできるだけ楽しいものにするよう最善を尽くすべきです。

これはオープンソースなのですから、みんな楽しむためにやっています（正直なところ…バグはその中で最も楽しい側面ではありませんが）。

#### 48.5.5 ヒーローのように感じてください

報告がクローズされたり、コメントに返答がなかったりすると、時間を無駄にしたと思うかもしれません。その想定は完全に間違っています。

開発者はごくわずかで、ユーザーは非常に多くいます。すべての人とやり取りし、多くをクローズすることなく一部のバグ報告を修正することは不可能です。

しかし Linux Mintは日々良くなっています。私たちのような人々と、あなたのような人々のおかげです。それは努力とフィードバックによって支えられています。

ここまで読んでくださった方、またはフィードバックやバグ報告に貢献してくださった方は、ヒーローのように感じてください。お互いの背中を叩いて称え合う時間を取ることは少なく、確かに十分にはできていません。

## 49章 よくある質問

### 50.1 アイデアや機能リクエストを送ることはできますか？

はい、もちろんです。Github の issue は必ずしもバグ報告である必要はありません。アイデアや機能リクエストでも構いません。

アイデアや機能リクエストを送信する際は、開発者がバグ報告ではないことがすぐにわかるように、issue のタイトルにそのことを示すようにしてください。

### 50.2 なぜアイデアや機能リクエストはクローズされるのですか？

以前は、「良い」アイデア（これは非常に主観的です）に関する issue はアイデアが実装されるまでオープンのままにし、「悪い」アイデア（または少なくとも緊急、実現可能、または十分に重要とは見なされなかったアイデア）はクローズされていました。

これは間違いでした。なぜなら、正当性と認識に焦点を当て、issue の作成者にトレーサビリティとアイデア実装の報告という、提供する余裕のないものを与えようとしていたからです。

現在のプロセスはずっとシンプルで、はるかに効率的です。アイデアを送信すると、それは処理されてからクローズされます。実装につながるかもしれませんし、チーム内の設計に関する議論につながるかもしれませんし、特定のリリースに向けて計画されロードマップに載せられるかもしれませんし、何も起こらないかもしれませんし、後で改善できるものとして人々の記憶に残るかもしれません。

いずれにせよ、アイデアが報告され、開発チームに理解された時点で、あなたの役割は完了です。あなたのアイデアに関する情報の収集と理解のプロセスが終了したら、issue はクローズできます。そのアイデアの最終的な実装の可能性は別の問題であり、issue をオープンのままにする理由にはなりません。

## 50章 一般的な概念

### 51.1 ローカリゼーション

> 注意: この章では翻訳の仕組みを説明します。ワークフローと技術をよりよく理解するのに役立ちますが、Linux Mintの翻訳を開始するために必須ではありません。スキップしたい場合は、次の章に直接進むことができます。

ソフトウェアアプリケーションとユーザーインターフェースは英語で設計されています。Linux Mintの開発者は、それらをローカライズするために Gettext と呼ばれるライブラリとツールセットを使用しています。

ソースコードを見ると、英語の単語や文章をラップするアンダースコア関数をよく目にします。例えば、`"Yes"` の代わりに `_("Yes")` と記述されます。このアンダースコアは Gettext を参照しており、文字列 "Yes" がローカライズされることを示しています。

以下は Python での例です。下記のコードは 2 つのボタンを作成します。両方とも「Yes」というラベルが付いていますが、button2 はローカライズされているのに対し、button1 はされていません。
```python
button1 = Gtk.Button()
button2 = Gtk.Button()

button1.set_label("Yes")
button2.set_label(_("Yes"))
```

実行時、button2 は適切に翻訳されますが、button1 は常に英語で表示されます。

このコードをフランス語で実行すると、「Yes」ボタンと「Oui」ボタンが表示されます。スペイン語で実行すると、「Yes」ボタンと「Sí」ボタンが表示されます。

もちろん、これが機能するためには、"Yes" に対するフランス語とスペイン語の翻訳が利用可能でなければなりません。利用可能でない場合、2 番目のボタンは英語で表示されます。

### 51.2 POT テンプレート

各プロジェクトについて、Linux Mintの開発者はすべての英語の単語と文章を抽出し、翻訳が必要なものすべてを PO テンプレートと呼ばれる `.pot` ファイルにまとめます。

開発者はそのファイルを Launchpad にアップロードし、翻訳者がそこで単語や文章を自分の言語に翻訳できるようにします。

### 51.3 PO ファイル

Linux Mint開発チームは Launchpad からすべての翻訳をダウンロードし、オペレーティングシステムにパッケージ化します。

翻訳は `.po` ファイルで構成され、コンパイルされて `.mo` ファイルとしてファイルシステム上（通常は `/usr/share/locale`）にインストールされます。これらは関連するアプリケーションにパッケージ化されるか、mint-translations（Mint ツール用）や cinnamon-l10n（Cinnamon 用）などの翻訳パッケージにパッケージ化されることもあります。

## 51章 翻訳

### 52.1 Launchpad の使用

#### 51.1.1 Launchpad アカウントの作成

Launchpad アカウントをまだお持ちでない場合は、登録ページを使用して新しいアカウントを作成してください。

アカウントの言語を編集し、流暢に話せるすべての言語を追加してください。

#### 51.1.2 あなたの言語の翻訳チームに参加する

すべての言語とその現在のステータスを確認するには、「Translation status by language」に移動し、「View all languages」をクリックします。

あなたの言語をクリックし、あなたの言語の翻訳を担当するチームの名前をクリックします。

「Join the team」をクリックします。

#### 51.1.3 Launchpad を使用して翻訳する

翻訳チームに参加したら、翻訳を開始できます。

あなたの言語をクリックし、未翻訳の項目があるプロジェクトを選択し、未翻訳の項目数をクリックします。

ページの上部で、レビューアーモード（Reviewer mode）になっていることを確認してください（そうでないと翻訳が自動的に承認されず、他の誰かがレビューするのを待つことになります）。

### 52.2 POEdit の使用

より速く翻訳したい場合は、翻訳を `.po` ファイルとしてダウンロードし、poedit と呼ばれるツールでそのファイルを編集し、編集した `.po` ファイルを Launchpad にアップロードし直すことができます。

#### 51.2.1 翻訳のダウンロード

プロジェクトを選択し、「Download translation」をクリックします。

ファイル形式として PO フォーマットを選択し、「Request Download」をクリックします。

Launchpad からメールが届くのを待ちます（少し時間がかかる場合があります）。メールには `.po` ファイルへの直接ダウンロードリンクか、`.po` ファイルを含む圧縮アーカイブへのダウンロードリンクが含まれています。

#### 51.2.2 POEdit の使用

POEdit をインストールするには、ターミナルを開いて以下を入力します：
```bash
apt install poedit
```

Launchpad から取得した `.po` ファイルを POEdit で開きます。

メニューを参照し、キーボードショートカットに慣れてください。これらのショートカットと組み込みのスペルチェッカーを使用すれば、Launchpad よりも POEdit ではるかに速く翻訳できます。

完了したら「Save」をクリックします。

#### 51.2.3 翻訳を Launchpad にアップロードし直す

Launchpad で「Upload translation」をクリックします。

`.po` ファイルを選択し、「Upload」をクリックします。

「Translation Import Queue」をクリックして、最新の翻訳インポートキューを表示します。

アップロードが「Needs Review」とマークされている場合は、「Edit」ボタン（ペンのシンボルで表示）をクリックし、正しいテンプレート（つまりプロジェクト）を選択して、「Approve」をクリックします。

## 52章 検証

### 53.1 翻訳の検証

#### 52.1.1 PO ファイルのダウンロード

翻訳が Launchpad 上にある場合は、「翻訳のダウンロード」で説明されているように、PO ファイルとしてダウンロードしてください。

ホームディレクトリに translations ディレクトリを作成し、PO ファイルをその中に入れます。

#### 52.1.2 mint-dev-tools のインストール

翻訳を検証するには、mint-dev-tools の一部である mint-check-translations というツールが必要です。

ターミナルを開いて以下を入力します：
```bash
apt install mint-dev-tools
```

#### 52.1.3 mint-check-translations で PO ファイルを検証する

翻訳をチェックするには、ターミナルを開いて以下を入力します：
```bash
mint-check-translations ~/translations
```

これにより翻訳チェックツールが開き、PO ファイル内のエラーがハイライトされます。

このツールは翻訳のミス（文法、スペルなど）はハイライトしませんが、翻訳が適切に構造化されており、翻訳対象のソフトウェアに影響を与えないことを確認します。特に、このツールは特別な意味を持つ文字が保持されていること、変数がまだ存在していることなどをチェックします。

> 注意: このツールは複数の PO ファイルをスキャンし、サブディレクトリを再帰的に処理できます。Linux Mintチームがすべての翻訳をチェックするために使用しています。

### 53.2 よくある間違い

#### 52.2.1 ソフトウェアアプリケーションにおいて

ソースコードを翻訳する際に最もよくある間違いは、変数を正しく扱わないことです。

以下に誤った翻訳の例をいくつか示します：

| 原文 | 翻訳 | エラー |
|---|---|---|
| `The file %s could not be found` | `Le fichier % s est introuvable` | `%s` ではなく `% s`（スペースが入っている） |
| `The file %s could not be found` | `Le fichier %d est introuvable` | `%s` ではなく `%d`（変数の型が異なる） |
| `The file %s could not be found` | `Le fichier est introuvable` | 変数が欠落 |
| `The file %(file)s could not be found` | `Le fichier %(fichier)s est introuvable` | 変数 `%(file)s` が欠落（名前が変更されている） |

変数が不正な形式である、欠落している、または名前が元のソースコードと一致しない場合、翻訳対象のアプリケーションがあなたの言語で実行された際にクラッシュする可能性があります。

#### 52.2.2 RST で書かれたドキュメントにおいて

RST ドキュメントを翻訳する際に最もよくある間違いは、二重引用符、矢印、または RST ディレクティブを正しく扱わないことです。

以下に誤った翻訳の例をいくつか示します：

| 原文 | 翻訳 | エラー |
|---|---|---|
| `` Open a terminal and type ``ls`` `` | `Ouvrez un terminal et tapez "ls"` | ` `` ` ではなく `"` を使用 |
| `` Click :guilabel:`Save` `` | `` Cliquez sur :guilabel:'Save' `` | `` ` `` ではなく `'` を使用 |
| `` Click :guilabel:`Save` `` | `` Cliquez sur :guilabel:`Save `` | `` ` `` が 1 つ不足 |
| `` Click :guilabel:`Save` `` | `` Cliquez sur guilabel:`Save` `` | `:` が 1 つ不足 |
| `` Click :menuselection:`Menu --> Save` `` | `` Cliquez sur :menuselection:`Menu -> Save` `` | `-->` ではなく `->` を使用 |

`` ` ``、`-->`、`:guilabel:`、`:menuselection:` などのディレクティブ、および `<` と `>` を使用するリンクは、ドキュメントの構造と外観を定義するために重要な特殊文字です。これらを正しく守り、内容を正確に翻訳するようにしてください。

元の文章に何か不足していると思われる場合は、元のドキュメントの修正を提案してください。元にない内容を翻訳に追加したり、内容を変更したりすることはできません。

#### 52.2.3 その他の間違い

##### 政治

コンテンツを翻訳する際、あなたの主な関心事はユーザーであるべきです。ユーザーエクスペリエンスが最も重要です。ソフトウェアとドキュメントは使いやすくあるべきであり、翻訳するテキストは読みやすく理解しやすくあるべきです。

ユーザーエクスペリエンスは、公式な言語の定義、言語保存政策、政治全般を含む他のいかなる考慮事項よりも重要です。

特定の単語の公式な翻訳がユーザーに一般的に知られていない、または使われていない場合は、それを使用すべきではありません。代わりに、ほとんどの人が使用している用語を優先してください。

目標はユーザーを教育したり何かを強制したりすることではありません。正確さと精密さは重要ですが、ユーザーエクスペリエンスほどではありません。あなたの周りの全員が A と言い、政府や辞書が B と言う場合、どちらに同意するかは関係なく、A を選んでください。

##### 翻訳すべきでないコンテンツの翻訳

画面上で英語で表示されているものは、英語のまま参照してください。

例えば、Linux Mintのブートメニューはユーザーがどの言語を使用しているかに関わらず「Start Linux Mint」と表示されます。したがって、ドキュメントが英語であるかどうかに関係なく、どのドキュメントでも「Start Linux Mint」として参照すべきです。

## 54章 技術

この章では、私たちが使用している技術の概要を説明します。

### 55.1 プログラミング言語

Linux Mintではさまざまなプログラミング言語を使用しています。すべてを知っている必要もなく、よく知っている必要もありません。どのプロジェクトで作業したいか、何を達成したいかによって異なります。

以下は私たちが最もよく使用する言語です。

Python — ターミナルやバックグラウンドで実行されるスクリプトは、通常 Bash または Python で書かれています。一部のソフトウェアアプリケーションとほとんどの設定ツールも Python で書かれています。Python の利点は、学習が容易で開発が速いことです。

C — 多くのソフトウェアアプリケーションとほとんどのライブラリは C で書かれています。C 言語は低レベルで、習得が難しく、開発が面倒ですが、高速なパフォーマンスを提供し、Linux で最もサポートされている言語です（すべてが C からアクセス可能です）。

Javascript — Cinnamon のグラフィカル要素、および Cinnamon のアプレット、デスクレット、拡張機能は Javascript で書かれています。

Vala — Vala は Slick Greeter（ログイン画面）で使用されています。

### 55.2 GNOME ツールキットとライブラリ

すべてのユーザーインターフェースは GTK3 ツールキットを使用しています。私たちの開発は GNOME ライブラリに大きく依存しており、特に Gio、GLib、GObject、dconf を多用しています。C ではこれらのライブラリに直接アクセスします。Python と Javascript では GObject Introspection を通じてアクセスします。

### 55.3 ツール

#### 54.3.1 開発環境

コードの記述と編集には好きなものを何でも使用できます。軽量なエディタを好む人もいれば、本格的な IDE を好む人もいます。好みの問題です。開発はすべて楽しむためのものなので、最も重要なのは使用するツールを気に入ることです。何を使うべきかわからない場合は、周りを見て、お気に入りを見つけるまでいくつかのエディタ/IDE を試してみてください。

チーム内の多くの開発者は Sublime を使用しています。
```bash
apt update
apt install sublime-text
```

Sublime をインストールしたら、その Package Control もインストールし、それを使用して GitGutter と TrailingSpaces 拡張機能をインストールしてください。

Visual Studio Code もチーム内で非常に人気があります。Atom、Brackets、Geany もチェックできます。完全な IDE が欲しい場合は、Eclipse や Netbeans もあります。

#### 54.3.2 バージョン管理

バージョン管理に関しては選択肢が少なく、全員が git のみを使用しています。すべてのコードは git でバージョン管理されています。とはいえ、必ずしも git コマンドラインを使用する必要はありません。git をより簡単に使用するためのいくつかのツールを紹介します。

gitk は見た目が古く時代遅れに見えます（Tcl/Tk で開発されています）が、コミット履歴を素早く確認したり、ブランチを作成したり、チェリーピックしたりするのに非常に便利です。
```bash
apt update
apt install gitk
cd ~/Sandbox/
git clone https://github.com/linuxmint/mintsystem.git
cd mintsystem
gitk
```

プロジェクトディレクトリから `gitk` と入力するだけでコミット履歴を確認できます。ブランチ名を指定してそのブランチを表示したり、サブディレクトリを指定して特定のディレクトリの履歴のみを表示したりすることもできます。

gitg は非常に似ていますが見た目が良く（Gtk を使用しています）、機能セットがわずかに異なります。
```bash
apt update
apt install gitg
cd ~/Sandbox/
git clone https://github.com/linuxmint/mintsystem.git
cd mintsystem
gitg
```

> 注意: gitg は mint-dev-tools に含まれています。gitg やその他の mint での開発に役立つツールがすでにインストールされています。

リポジトリからは git-cola や git-gui もチェックできます。より完全なソリューションをお探しの場合は、Gitkraken をご覧ください。最後に、IDE/エディタで利用可能なプラグインと機能をチェックしてください。Visual Studio Code、Atom、Sublime は特に Git と Github の多くのサポートが付属しています。

#### 54.3.3 Glade

ユーザーインターフェースをプログラミング言語で記述することも、Glade を使用してマウスで描画することもできます。Glade は GTK ユーザーインターフェースを設計・編集し、XML（.glade または .ui ファイル）として保存するためのツールです。
```bash
apt update
apt install glade
```

ユーザーインターフェースが保存されたら、プログラムにそのファイルを開くよう指示するだけで、そこからウィジェットにプログラム的にアクセスできます。私たちのプロジェクトの多くは、コードとユーザーインターフェースを分離しています。

#### 54.3.4 devhelp

Devhelp は、コンピュータにインストールされている開発ライブラリのリファレンスマニュアルを表示します。ほとんどのライブラリについて、ドキュメントは -dev または -doc パッケージに含まれています（例えば、GTK3 で作業している場合は、libgtk-3-dev と libgtk-3-doc をインストールしてください）。
```bash
apt update
apt install devhelp
```

DevHelp をアプリケーションメニューから起動し、ライブラリのリファレンスマニュアルを参照または検索できます。特定の関数の構文や引数を確認する必要がよくあります。オンラインで検索することなく、ローカルで情報を取得できるのは便利です。

#### 54.3.5 d-feet

一部のプログラムは DBus を使用して他のプログラムと通信します。私たちは d-feet を使用して DBus の参照とトラブルシューティングを行います。
```bash
apt update
apt install d-feet
```

d-feet を使用すると、DBus 上のサービスをすばやく見つけ、そのインターフェースを参照し、一部の関数を手動で呼び出すこともできます。

#### 54.3.6 meld

Meld はビジュアル差分ツールです。2 つのファイル間の差分を表示し、それを非常にうまく行います。

#### 54.3.7 その他の便利なツール

設定のほとんどは dconf に保存されており、コマンドラインから gsettings を使用して確認または変更します。グラフィカルに行いたい場合は、dconf-editor をインストールできます。awf は GTK テーマで作業する際にウィジェットをテストするのに便利です。

### 55.4 XApps

2016 年に「X-Apps」というプロジェクトが開始され、従来の GTK デスクトップ環境向けの汎用アプリケーションを制作しています。

このプロジェクトの背景にある考えは、特定の環境の外ではもはや適切に統合できなくなったアプリケーション（これは GNOME アプリケーションの増加する数に当てはまります）を置き換え、デスクトップ環境に同じコアアプリケーションのセットを提供することです。これにより、各変更、開発される各新機能、加えられる各小さな改善が 1 つの環境だけでなく、すべての環境に恩恵をもたらします。

X-Apps のコアアイデアは以下の通りです：モダンなツールキットと技術の使用（HiDPI サポートのための GTK3、gsettings など）、従来のユーザーインターフェースの使用（タイトルバー、メニューバー）、どこでも動作すること（汎用的で、デスクトップやディストリビューションに依存しない）、ユーザーがすでに享受している（または一部のディストリビューションではすでに失われた）機能の提供、下位互換性（できるだけ多くのディストリビューションで動作するため）。

Linux Mint内では、ユーザーは X-Apps に適応する必要がありませんでした。多くの場合、人々がすでに使用していたアプリケーションと非常に似ているか、まったく同じだったからです。例えば、Totem 3.18 は Linux Mint17 に同梱された Totem 3.10 とは根本的に異なっていましたが、Xplayer 1.0（Linux Mint18 のデフォルトメディアプレーヤー）はまったく同じでした。

X-Apps の目標は車輪を再発明することではありません。むしろその正反対で、すでに楽しんでいたアプリケーションのメンテナンスを保証し、複数のデスクトップ環境に恩恵をもたらす方向にその開発を導くことです。3 つの異なるテキストエディタや 5 つの異なる電卓などを開発する意味はありません。これらのようなプロジェクトに取り組む際、その価値を最大限に発揮したいと考えています。テキストエディタの改善は 1 つのエディションだけでなく、すべてのエディションに恩恵をもたらすべきです。

Linux Mintの 3 つのエディションすべてに同じ XApps ライブラリとアプリケーションが同梱されています。XApps の開発に取り組む際、私たちの開発努力はすべてのデスクトップの改善に集中しています。

#### 54.4.1 libxapp

XApps ライブラリです。クロスデスクトップに関するものはすべてここに入ります。GObject Introspection を通じて Python と JS でも利用可能です。このプロジェクトは C で開発されており、ソースコードは Github で公開されています。

#### 54.4.3 xed

Xed は Pluma をベースにしており、デフォルトのテキストエディタとして機能します。このプロジェクトは C で開発されており、ソースコードは Github で公開されています。

#### 54.4.4 xviewer

Xviewer は Eye of GNOME をベースにしており、デフォルトの画像ビューアーとして機能します。このプロジェクトは C で開発されており、ソースコードは Github で公開されています。

#### 54.4.5 xplayer

Xplayer は Totem をベースにしており、音楽と動画のデフォルトメディアプレーヤーとして機能します。このプロジェクトは C で開発されており、ソースコードは Github で公開されています。

#### 54.4.7 pix

Pix は gThumb をベースにしており、写真を整理するためのアプリケーションです。このプロジェクトは C で開発されており、ソースコードは Github で公開されています。

#### 54.4.8 blueberry

Bluetooth ツール blueberry は、システムトレイサポートを備えた gnome-bluetooth のフロントエンドです。GNOME Bluetooth フロントエンドは gnome-bluetooth から削除され、gnome-control-center の一部となり、本質的に gnome-bluetooth を GNOME の外では使い物にならなくしました。Blueberry はその不足しているフロントエンドを提供し、他の GTK デスクトップが gnome-bluetooth を簡単に使用できるようにします。このプロジェクトは Python で開発されており、ソースコードは Github で公開されています。

## 55章 開発

### 54.1 ビルド

mint-dev-tools をインストールすれば、Linux Mintプロジェクトをソースからビルドするのは非常に簡単です。

#### 55.1.1 ソースコードのダウンロード

`git clone` を使用して Github からソースを取得します。例えば、mintinstall のソースを取得するには以下のように入力します：
```bash
cd ~/Sandbox
git clone https://github.com/linuxmint/mintinstall.git
```

#### 55.1.2 プロジェクトの初回ビルド

`mint-build` を使用してプロジェクトを初めてビルドします。mint-build はプロジェクトをビルドするだけでなく、ビルド依存関係（ビルドを成功させるために必要なパッケージ）も取得してインストールします。

mintinstall をビルドするには、以下のように入力します：
```bash
cd ~/Sandbox/mintinstall
mint-build
```

ビルドが完了すると、生成されたバイナリ .deb パッケージは親ディレクトリ（この例では ~/Sandbox）に配置されます。

#### 55.1.3 プロジェクトのビルド

特定のプロジェクトのビルド依存関係がすべてインストール済みの場合（これは mint-build がプロジェクトの初回ビルド時に行います）、`dpkg-buildpackage` を呼び出すだけでより速くビルドできます。

mintinstall をビルドするには、以下のように入力します：
```bash
cd ~/Sandbox/mintinstall
dpkg-buildpackage
```

#### 55.1.4 ビルド順序の遵守

ビルドしようとしているプロジェクトの新しい変更が、別のプロジェクトの新しい変更を必要とする場合、そのプロジェクトを先にビルドしてインストールする必要があるかもしれません。一般的に、mint-common と xapps を最初にビルドすることをお勧めします。

### 54.2 Romeo

開発チームは Romeo を使用して新しい BETA/ALPHA 機能をプッシュします。

> 重要: Romeo には不安定なビルドと開発者が Github にプッシュした最近の変更が含まれています。これを使用すると、安定版から不安定版にアップグレードされ、リグレッションが発生したり、まったく動作しなくなる可能性があります。

#### 55.2.1 Romeo の有効化

コンピュータで Romeo を有効にするには、ソフトウェアソースを開き、「不安定なパッケージ（romeo）」オプションにチェックを入れます。

#### 55.2.2 不安定版へのソフトウェアのアップグレード

アップデートマネージャーを使用してソフトウェアを更新し、不安定版にアップグレードします。

#### 55.2.3 安定版へのダウングレード

安定版に戻すには、Timeshift のスナップショットを復元するか、Romeo を無効にし（ソフトウェアソースを使用）、APT キャッシュを更新して、ソフトウェアソースツールのメンテナンス → 外部パッケージのダウングレードセクションを使用します。

### 54.3 コーディングガイドライン

#### 55.3.1 コーディングスタイル

シンプルさ — 複雑な命令よりもシンプルな命令を好んでください。たとえそれがより多くの行を使用したりコードを重複させたりすることを意味しても構いません。ワンライナー、複雑な条件、言語固有の機能、抽象的/汎用的なパターンは避けてください。コードに説明が必要な場合はコメントを書くか…さらに良いのは、よりシンプルな方法で書き直すことです。

一貫性 — 貢献しているプロジェクトで使用されているコーディングスタイルを採用してください。これにより、新しいコードと既存のコードの間の一貫性が保証されます。

インデント — 新しいプロジェクトや新しいファイルでは、タブを使用しないでください。代わりに 4 つのスペース文字を使用してください。

末尾のスペース — コード内に末尾のスペースを残さないでください。

> ヒント: Sublime では、TrailingSpaces プラグインをインストールすると、末尾のスペースが自動的にハイライトされ、簡単に削除するオプションが提供されます。

最大行長 — コードを 120 列以内に収めてください。コードの行が 120 文字より長い場合は、2 行以上に分割してください。

> ヒント: Sublime では、表示 → ルーラー → 120 を選択してルーラーを表示できます。

### 54.4 付録：Cinnamon Javascript 最適化テクニック

これは Cinnamon における Javascript 最適化テクニックに関する暫定的な章です。Cinnamon のデザインが記述され、このセクションの内容が適切な場所に収まった時に、開発者ガイドの一部となります。

#### 55.4.1 備考

これらの最適化テクニックの一部は理にかなっておらず、すべてを説明できるわけではありませんが、体系的にテストされました。Jason だけがチーム内でこれらの影響を確認しています。彼はマルチモニターで低速な CPU を使用し、NVIDIA ドライバーを備えた低遅延カーネルを実行しています。これらは Cinnamon 4.0 でテストされました。パフォーマンスの向上は、ウィンドウの移動や Visual Studio Code でのテキスト選択時の入力遅延の面で確認されています。これらの変更は windowManager.js でテストされました。これは Cinnamon 内で常に実行され、単一の実行スレッド内で主要な位置を占める領域です。

#### 55.4.2 gsettings シグナルリスナーの総数の削減

リスナーの数を減らすことは、パフォーマンスに大きなプラスの影響を与えます。

#### 55.4.3 シグナルリスナーでの宣言済み関数の使用

以下のような使用法：
```javascript
settings.connect('changed::property', (s, k) => {
    this.property = s.get_int(k);
});
```

は、以下よりも遅いことがわかりました：
```javascript
settings.connect('changed::property', (s, k) => this.setProperty(s, k));
```

つまり、関数を宣言してコールバック内でその関数を参照する方が、コールバック内で匿名の命令ブロックを使用するよりも速かったのです。影響は大きなものでした。

#### 55.4.4 コールバックの集約
```javascript
settings.connect('changed::int_property1', (s, k) => this.setProperty1(s, k));
settings.connect('changed::string_property2', (s, k) => this.setProperty2(s, k));
```

は、以下よりも遅いことがわかりました：
```javascript
settings.connect('changed::int_property1', (s, k) => this.setProperty(s, k, 'int'));
settings.connect('changed::string_property2', (s, k) => this.setProperty(s, k, 'string'));
```

もちろん setProperty() は遅くなりますが、通常それは重要ではなく、プロジェクト全体は速くなります。影響はそれほど大きくなく、この最適化はおそらく windowmanager.js のようなクリティカルパスにのみ適しています。

#### 55.4.5 プロパティの小さなオブジェクトへのグループ化

`this.smallobject.property` は `this.property` よりも高速です。Main.wm のような大きなオブジェクトにプロパティを追加しないことが考え方です。そのため、`Main.wm.desktop_effects_enabled` の代わりに `Main.wm.settings.desktop_effects_enabled` を使用します。影響はプラスですが微妙であり、この最適化はおそらく windowmanager.js のようなクリティカルパスにのみ適しています。

#### 55.4.6 プロパティに対するハッシュマップの使用

`this.smallobject['property']` は `this.smallobject.property` よりも高速です。そのため、`Main.wm.desktop_effects_enabled` の代わりに `Main.wm.settings['desktop_effects_enabled']` を使用します。影響はプラスですが微妙であり、この最適化はおそらく windowmanager.js のようなクリティカルパスにのみ適しています。
